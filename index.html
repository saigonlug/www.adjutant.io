Case 01 / Banking platform

Billions moving.
Basic facts missing.

Billions of USD moved through a banking platform that couldn’t tell if a lender was married.

GDPR, SOC 2, ISO 27001? The easy part. Preventing data poisoning and PII leakage across billions of USD in transactions? The hard part.

↳

A structured foundation.
A migration out of the mess.

What happened

The owner wanted to onboard banks quickly, each with different org charts, processes, and policies. “Flexible” should have meant configurable structures and workflows. The product requirements stayed vague, and the contracted tech team removed the rules from the data instead.

PostgreSQL was treated like an unconstrained document store. One customer had “Married.” Another had no marital-status field. Another had a blank, a space, or a value in another language. Anyone—or any process—could write almost anything.

Our consultant helped untangle the records, define a structured model, and migrate the legacy data. Real flexibility needed explicit identities, validated values, and rules the database could enforce.

Case 02 / Client onboarding

Major new client.
Another total rebuild.

Everyone loves onboarding a major financial institution. It is the kind of client every growing business wants.

Rebuilding the platform from scratch for every client because the tech team made one strategic data mistake? Not so much.

↳

A reusable core.
Room for each client’s workflow.

What happened

Documents moved between officers for processing, compliance, and audit. The software reproduced the physical numbering and handoffs so literally that each institution required its own variation of the platform.

Our consultants helped separate document identity from workflow and rebuild the core to support different institutional needs. The work addressed tightly coupled data and processing rules that made the business difficult to scale.

Case 03 / Logistics platform

A 96xlarge AWS instance.
Still down every
two weeks.

They were paying for a gigantic AWS 96xlarge instance to prop up a single-point-of-failure PostgreSQL database. It still took a fast-growing logistics operation completely offline every two weeks.

Work fell back to pen, paper, and phone calls like it’s the 1990s. The machine was enormous. A catastrophic software and data architecture mistake remained underneath it.

↳

Operations and analytics, decoupled.
Insight without the collision.

What happened

A load balancer spread requests across copies of the same backend monolith. Every copy hammered the same master database. Reporting and analytics hammered it too. More application servers only sent more work to the same bottleneck.

Even a 96xlarge AWS instance could not fix that design. Production and analytics competed for the same resources. A bigger box was an expensive way to keep the same failure mode.

Our consultant helped move the platform toward a service-oriented architecture, separating data and workloads. Real-time analytics moved to an independent platform so insight no longer competed with operations.
